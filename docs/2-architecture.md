# Devo 编码代理系统架构设计文档

**版本**：1.0.0

**定位**：一个以会话为核心、对话驱动的自主编码智能体。所有文件版本管理由用户通过 Git 手动控制，代码执行在本地原生系统环境中通过 Python 执行器完成。系统只负责代理循环、工具调用、审批和事件流，不做任何自动版本回溯或容器隔离。

---

## 1. 总体架构

三层分离：**核心层**、**任务处理层**、**接口层**。外部 UI 通过 HTTP 与接口层通信，采用 **SSE（Server-Sent Events）+ REST API** 实现实时反馈与指令下发。

```
┌─────────────────────────────────────┐
│               UI 层                  │
│  CLI / Web / IDE 插件                │
└────────────┬────────────────────────┘
             │ HTTP (REST) + SSE
┌────────────▼────────────────────────┐
│            接口层 (API)              │
│  REST API · SSE 事件流 · 审批桥接    │
└────────────┬────────────────────────┘
             │ Go 接口
┌────────────▼────────────────────────┐
│         任务处理层 (Task)            │
│  工具集 (写文件/执行命令/搜索等)     │
│  Python 统一沙箱执行器               │
│  LLM 客户端封装 · Token 计量器       │
└────────────┬────────────────────────┘
             │ Go 接口
┌────────────▼────────────────────────┐
│           核心层 (Core)              │
│  会话生命周期 · 对话驱动 Agent Loop  │
│  审批门控（含超时/风险分级）         │
│  上下文压缩 · 事件总线 · 消息回滚    │
│  长期记忆管理器 · 经验固化器         │
│  Skills 管理器 · agents.md 加载器    │
│  会话存档 · 并发会话隔离             │
│  Token 计量协调 · 崩溃恢复           │
└─────────────────────────────────────┘
```

- **核心层**：纯逻辑，管理会话、驱动循环、控制审批、发布事件、压缩上下文、管理长期记忆与技能进化、生成会话存档、处理崩溃恢复。不自动管理文件版本。
- **任务处理层**：提供工具执行能力（含内置工具和 MCP 动态工具），并强制实施路径安全校验。通过 Python 子进程在原生系统中统一执行命令。不依赖 Docker。内置 Token 计量器，追踪每次 LLM 调用的 Token 消耗。
- **接口层**：将核心层能力暴露为 REST API 和 SSE 事件流，实现审批桥接，提供会话暂停/恢复语义，暴露 Token 消耗、统计查询与会话存档。

### 1.1 部署模型

Devo 采用 **"本地核心 + 可选团队服务"** 的混合部署模式。

**本地核心（必需）**
- 核心层、任务处理层、接口层运行在开发者的个人电脑或专属开发机上。
- 直接访问本地文件系统、Shell 环境和开发工具链。
- 长期记忆、进化技能、会话数据默认存储在 `~/.devo/`。
- 审批门控、路径安全等安全机制均基于本地环境实施。

**可选团队服务（增强）**
- 一个轻量级的中心服务，提供以下**唯一**职责：
  - **统计与审计**：接收各本地实例上报的 Token 消耗摘要，按成员、项目、时间聚合，提供成本估算和预算预警。
  - **远程协作**：中转审批请求到团队成员，支持旁观 Agent 状态（只读）。
- 该服务**绝对不**：
  - 不存储代码
  - 不执行代码
  - 不存储完整对话内容
- 数据上报遵循最小化原则，仅上报统计所需的元数据，项目路径做哈希脱敏处理。

## 2. 核心层详细设计

核心层是系统的大脑，负责会话生命周期、代理循环、审批门控、事件发布、上下文压缩、长期记忆管理、经验固化、会话存档、崩溃恢复，以及**仅限对话历史的消息回滚**。它不参与任何文件版本管理。每个会话拥有完全独立的执行上下文和事件通道。

### 2.1 会话模型

一个会话（Session）包含：

| 组成部分 | 说明 |
| :--- | :--- |
| **唯一标识** | 会话 ID |
| **消息历史** | 完整有序的消息列表（用户、助手、系统、工具调用结果） |
| **工作目录路径** | 会话关联的本地项目目录，创建会话时必须提供合法路径，系统只在该目录范围内操作 |
| **代理循环状态** | Idle / Processing / AwaitingApproval / Paused / Completed / Archived |
| **元数据** | 创建时间、最后活跃时间、会话标题、当前信任级别、审批策略配置、子进程 PID、工具调用上限（tool_call_limit，默认 50）、当前工具调用计数等 |
| **上下文压缩状态** | 记录已压缩的消息范围、摘要内容，用于保证长会话的连续性 |
| **事件总线和事件历史** | 会话专属的实时事件发布通道及已发送事件的滚动历史，用于 SSE 重连补推 |
| **审批配置** | 当前有效的审批策略（含按操作类型的细粒度策略）及审批超时时间 |
| **活跃 SSE 连接计数** | 用于判断客户端是否在线，断连时自动暂停会话 |
| **Token 消耗累计** | 会话级别的 Token 消耗汇总（输入/输出/合计），由 Token 计量器实时更新 |
| **会话存档路径** | 会话的 Markdown 存档文件路径（项目内 `<工作目录>/.devo/sessions/<id>.md` 或全局 `~/.devo/sessions/<id>.md`） |

**注意**：系统不维护文件快照。文件状态完全由 Git 仓库反映，用户自行 commit、reset 等。系统仅在工作目录中读写文件。

### 2.2 会话生命周期与状态

| 状态 | 说明 |
| :--- | :--- |
| `Idle` | 等待用户输入 |
| `Processing` | 代理循环正在运行，SSE 持续推送事件 |
| `AwaitingApproval` | 暂停等待用户审批某个操作，设有超时计时器 |
| `Paused` | 用户主动暂停或 SSE 连接全部断开，代理循环挂起，可恢复 |
| `Completed` | 用户标记完成 |
| `Archived` | 归档，不可再交互 |

状态流转规则：
- **暂停与恢复**：当代理处于 `Processing` 状态时，用户可通过接口**主动暂停**，系统将当前步骤执行完安全收尾后转入 `Paused`；若会话的所有 SSE 连接均断开（客户端离线），系统自动将会话置为 `Paused` 并挂起循环。恢复时，用户重新连接 SSE 后通过接口**显式恢复**，或直接发送新消息，代理将从中断点继续循环。
- **取消**：用户在任意 `Processing` 或 `AwaitingApproval` 状态下可通过 HTTP 接口强制取消当前循环，状态重置为 `Idle`，LLM 上下文中的未完成工具调用视为失效。
- **审批超时**：在 `AwaitingApproval` 状态下若超出配置时间仍未收到审批决策，系统自动视为"拒绝"，并回到 `Processing` 状态继续循环，同时向 LLM 注入拒绝反馈。超时后收到的补交审批请求将被忽略。
- **完成与会话归档**：用户可将 `Idle`、`Paused` 或 `Completed` 状态的会话标记为 `Completed`；若正在 `Processing` 则系统先执行取消逻辑再切换。`Completed` 状态的会话可进一步归档为 `Archived`。
- **工具调用上限暂停**：当循环因达到工具调用上限而终止时，状态切回 `Idle`，并推送 `session_state_change` 事件（`reason: tool_limit_reached`）。用户可通过发送“继续”或直接输入新消息，系统将注入中断上下文并重置工具调用计数器，自动恢复循环。详见 2.5。
- **归档后的约束**：处于 `Archived` 状态的会话，拒绝以下操作并返回 409（Conflict）：
  - 发送新消息（`POST /messages`）
  - 响应审批（`POST /approve`）
  - 状态控制（`POST /cancel` / `POST /pause` / `POST /resume`）
  允许的操作：查看消息历史、浏览文件、查看记忆、查看 Token 消耗、下载存档。

### 2.3 消息回滚（仅对话历史）

用户可请求回滚到某条消息。核心层执行：

1. 定位目标消息 ID。
2. **完整性检查与吸附**：确保回滚后的消息历史不会在"工具调用请求"和"工具调用结果"之间截断，避免破坏 LLM 工具调用协议。
   - 若目标消息是**助手消息且包含工具调用**，且其后存在对应的工具结果，则自动将回滚点**后移**至该工具结果之后，完整保留整个工具调用回合。
   - 若目标消息是**工具结果**，且其前存在对应的工具调用请求，则自动将回滚点**前移**至该工具调用请求之前，一并删除这个不完整的工具调用回合。
   - 若目标消息是普通用户/助手消息，无需吸附。
3. 截断消息历史，删除吸附后确定的回滚点之后的所有消息。
4. **不操作任何文件**。文件状态停留在最后一次工具操作之后的样子。由用户自行决定是否用 Git 回退。
5. 在消息历史中插入一条系统消息记录回滚操作（包含回滚目标和时间；若发生吸附，同时说明实际回滚位置及原因）。
6. **文件状态同步检测**：回滚完成后，系统对比工作目录中最近被工具修改的文件时间戳与回滚点。若发现回滚点之后有工具调用产生的文件变更，则在 SSE 事件流中发布一个**警告事件**，提示用户文件状态可能与当前对话不一致，并建议使用 Git 检查。
7. 重置代理状态为 `Idle`，同时清空或重置上下文压缩状态。
8. **存档同步**：回滚完成后，异步触发生成新的存档文件，反映回滚后的消息历史。

回滚后，用户可以直接从该点继续对话，无需系统介入文件版本。

### 2.4 会话恢复与崩溃恢复

**正常恢复**：
- 会话数据（消息历史、状态、元数据、压缩状态）持久化到嵌入式数据库。
- 恢复时从存储加载，重建消息列表和状态，工作目录由用户提供或从元数据中获取。
- 若工作目录路径已不存在或无权访问，会话状态置为 `Paused` 并发出错误事件，提示用户修正路径。
- 不恢复任何文件快照，因为系统不保存它们。

**崩溃恢复**：
- 服务启动时，扫描持久化存储中所有非终态会话（`Idle`、`Processing`、`AwaitingApproval`、`Paused`）。
- 对状态为 `Processing` 或 `AwaitingApproval` 的会话，执行**崩溃恢复重置**：
  1. 将状态强制切回 `Idle`。
  2. 在消息历史中插入一条系统消息，内容为：*"系统检测到上次服务异常中断，当前会话已重置。未完成的工具调用已丢弃，请检查文件状态。"*
  3. 清理可能残留的孤儿子进程（通过会话元数据中记录的子进程 PID 进行终止，这些子进程为 Python 解释器进程）。
  4. 异步触发会话存档更新，反映崩溃重置后的状态。
  5. 若有活跃 SSE 连接，推送 `session_state_change` 事件通知前端（`reason: error`）。
- `Paused` 状态的会话保持不变（因其子进程已安全收尾）。
- `Idle` 状态的会话无需处理。

### 2.5 代理循环（对话驱动）

循环由用户消息触发：

1. 将用户消息追加到历史。
2. **构建增强版 LLM 上下文**（顺序固定）：
   - 基础系统提示词
   - 当前会话已激活的 **Skills 指令集**（项目内 > 全局 > 社区，同名覆盖）
   - 从 **`agents.md`** 加载的项目级规则（若存在）
   - **长期记忆管理器** 检索到的相关用户记忆和项目记忆
   - 工作目录文件结构摘要
   - 上下文压缩后的最近对话历史
3. 与 LLM 交互的循环（每一步均通过 SSE 实时推送事件）：
   - LLM 返回文本 → 本轮结束，追加回复到历史，推送 `message_complete` 事件（附带 Token 消耗），异步更新会话存档。
   - LLM 返回工具调用请求 → 核心层解析工具名和参数，通过 SSE 推送 `tool_call_request`。
   - 若工具需要审批，根据操作风险等级和当前审批策略判断是否需要用户确认。需要确认的通过审批门控暂停等待；自动批准的则直接进入执行，仅通过 SSE 推送通知事件。启动审批超时计时器，SSE 推送 `approval_required`。被拒或超时后向 LLM 注入拒绝/超时信息，继续循环或终止。
   - 审批通过后，调用任务处理层的工具执行函数，获得结果，通过 SSE 推送 `tool_result`，异步更新会话存档。
   - 将工具结果包装为工具消息，追加到历史，继续请求 LLM。
   - **每次 LLM 调用完成后，Token 计量器推送 `token_usage` 事件**，包含本次调用的输入/输出 Token 数和会话累计。
4. 循环终止条件与原因：
   - **正常完成**：LLM 返回文本回复且无后续工具调用。状态切回 `Idle`，推送 `session_state_change`（`reason: completed`）。
   - **用户取消**：用户通过接口取消。状态切回 `Idle`，推送 `session_state_change`（`reason: cancelled`）。
   - **达到工具调用上限**：当前循环的工具调用次数达到会话配置的 `tool_call_limit`（默认 50）。此时：
     - 结束当前循环，但**不清除消息历史中未完成的工具调用上下文**。
     - 状态切回 `Idle`，推送 `session_state_change`（`reason: tool_limit_reached`），前端展示醒目的系统消息：*"AI 已进行 N 次工具调用，达到上限暂停。任务尚未完成，是否继续？"*
     - 系统在消息历史中自动追加一条系统消息，标记因上限暂停，并提示用户输入“继续”可续上预算。
   - **不可恢复错误**：发生系统级错误。状态切回 `Idle`，推送 `session_state_change`（`reason: error`）和 `error` 事件。
5. 循环过程中，核心层会定期检查会话的取消标记（由 HTTP 接口设置）。一旦发现已取消，立即中断当前步骤，清理子进程，推送 `session_state_change` 事件（`reason: cancelled`），状态切回 `Idle`。

**工具调用上限的恢复机制（“接着修”）**：
- 当用户在因 `tool_limit_reached` 暂停的会话中发送新消息（如“继续”），系统识别到上一轮终止原因为 `tool_limit_reached`，执行以下恢复流程：
  1. 在消息历史中注入一条系统消息：*“上一次任务因达到工具调用上限（N 次）而暂停。当前任务尚未完成，请从中断点继续。已完成的工作保留在文件系统中，无需重复执行。”*
  2. **重置当前会话的工具调用计数器**，新一轮循环获得全新的上限配额。
  3. 将用户的“继续”消息追加到历史，正常触发代理循环。
- 若用户在暂停期间发送的不是“继续”，而是全新的任务指令，系统同样先注入中断上下文再追加用户消息，确保 LLM 了解之前的状态，但 LLM 可根据新指令重新规划任务。

### 2.6 Token 计量器（Token Meter）

Token 计量器嵌入在代理循环中，由任务处理层的 LLM 客户端封装提供原始数据，核心层负责汇总和事件发布。其职责是为成本透明化、上下文压缩决策和预算管控提供数据基础。

**计量点**：
- 在 **构建 LLM 上下文** 时，计算完整的输入文本 Token 数，得到 `input_tokens`。
- 在 **LLM 流式返回** 时，累加所有输出文本和工具调用参数的 Token 数，得到 `output_tokens`。
- 对于支持推理的模型，可选单独记录思考 Token。

**SSE 事件暴露**：
- 每次 LLM 调用完成后，推送 `token_usage` 事件，包含：
  - `step`: 当前步骤标识
  - `input_tokens` / `output_tokens`: 本次调用消耗
  - `session_total_tokens`: 当前会话累计消耗
- `message_complete` 事件中附带 `total_step_tokens`，表示整轮用户请求的 Token 成本。
- `context_compressed` 事件中附带 `tokens_removed`，表示压缩释放的 Token 量。

**REST API 暴露**：
- `GET /api/v1/sessions/{id}/usage`：获取会话级别的 Token 消耗汇总。
- `GET /api/v1/usage/stats`：本地统计聚合，支持按项目、会话、日期分组。

### 2.7 上下文压缩

为避免长对话超出 LLM 最大上下文窗口，核心层内置**滑动窗口 + 摘要**机制：

- 系统设定一个上下文消息数量阈值（可配置）和 Token 总量预算。
- 当消息历史超出阈值时，对最早的消息段进行压缩：
  - 保留所有系统消息、回滚记录和工具调用结果的关键元数据。
  - 将用户和助手的连续对话片段交由 LLM 生成一段简洁摘要。
  - 将摘要以系统消息形式插入历史头部，并删除已被摘要覆盖的原始消息。
- 压缩后的历史由"头部摘要 + 最近完整消息"组成。
- 每次压缩完成后通过 SSE 推送 `context_compressed` 事件（附带 `tokens_removed` 字段），同时异步更新会话存档，在存档末尾追加"上下文压缩摘要"附录。

该机制对用户透明，摘要内容可在界面中查看。

### 2.8 系统提示词与配置

系统提示词是指导 LLM 行为的关键配置，包含角色定义、工具签名列表、工作目录约束、审批规则、迭代修复策略等。每次构建上下文时动态组装，由以下部分按序拼接：

- **基础系统提示词**：角色定义、核心行为准则、安全底线。
- **Skills 指令集**：从 Skills 管理器获取当前激活技能的系统指令文本。
- **agents.md 项目规则**：从 agents.md 加载器获取的项目级编码规范、架构约束等。
- **长期记忆**：从长期记忆管理器检索的相关用户偏好和项目经验。
- **动态信息**：当前信任级别、会话 ID、工作目录路径、审批策略、工具调用上限与当前计数等实时变量。

系统提示词支持会话级覆盖，允许创建会话时传入自定义片段追加到基础提示词之后。

### 2.9 工作目录文件结构摘要

每次代理循环启动时（或在用户消息后），系统自动生成一份工作目录摘要：

- **生成方式**：调用 `list_files` 工具扫描工作目录，生成目录树。
- **粒度控制**：默认列出全部文件，遵循 `.gitignore` 规则，可配置最大深度和文件数量上限。
- **内容增强**：对于关键代码文件，可自动附加其前 N 行内容。
- **缓存与更新**：如果两次循环之间未执行任何文件修改，可复用上一次摘要。

### 2.10 审批门控与风险分级

审批门控是系统的核心安全防线，在保证安全的同时通过风险分级机制避免审批疲劳，保持"点个头就行"的轻量化体验。

#### 2.10.1 操作风险分级

所有需要审批的操作按风险等级分为三级，系统预设默认审批策略：

| 风险等级 | 操作类型 | 默认策略 | 理由 |
| :--- | :--- | :--- | :--- |
| **高** | `execute_command`（执行命令） | `always_ask` | 命令执行风险最大，是安全的最后防线。 |
| **中** | `file_write_new`、`file_write_overwrite`、`file_edit`（文件写入） | `always_ask` | 涉及代码修改，但有 diff 可供审查，用户可在熟悉后自行降级。 |
| **低** | `memory_update`（记忆更新）、`solidify_skill`（技能固化）、网络访问（仅限读取操作） | `auto_approve` | 记忆和技能是"学习"行为，打断感强；它们有独立的撤销机制（手动删除记忆/技能），风险可控。自动批准后通过 SSE 推送通知事件，保持透明但不打断工作流。 |

#### 2.10.2 审批策略配置

用户可以按操作类型自定义审批策略，覆盖系统默认值。支持的策略级别：

| 策略级别 | 行为 |
| :--- | :--- |
| `always_ask` | 始终询问，暂停等待用户确认。 |
| `session_trust` | 本次会话内自动批准。 |
| `full_trust` | 永久自动批准（跨会话）。 |
| `auto_approve` | 自动批准，但通过 SSE 推送通知事件告知用户。 |

用户可通过 `PUT /api/v1/sessions/{id}/approval-policy` 接口在运行时动态调整各操作类型的审批策略。配置存储在会话元数据中。

#### 2.10.3 审批超时与审批中的文件差异展示

- **审批超时**：每个审批请求都带有一个可配置的超时时间（默认 5 分钟）。超时后系统自动视为"拒绝"，并注入相应反馈给 LLM，继续循环。超时后收到的补交审批响应将被丢弃并记录警告。
- **文件差异展示**：对于文件编辑操作（`file_write_overwrite` 和 `file_edit`），系统在推送 `approval_required` 事件前自动生成新旧内容 diff（unified diff 格式），附加在事件的 `details.diff` 字段中，供前端渲染高亮对比视图。
- **operation_type 枚举**：
  - `file_write_new`：新建文件
  - `file_write_overwrite`：完全覆盖已有文件
  - `file_edit`：精确编辑（查找替换或 Patch）
  - `execute_command`：执行命令
  - `memory_update`：更新记忆
  - `solidify_skill`：固化技能

### 2.11 并发会话隔离

系统支持多个会话同时存在且独立运行。隔离原则：
- **事件通道隔离**：每个会话拥有独立的事件总线实例，不同会话的 SSE 流完全隔离。
- **工具执行上下文隔离**：任务处理层为每个会话维护独立的工作上下文（工作目录、环境变量集合）。
- **Python 执行器隔离**：每次 `execute_command` 调用启动独立子进程，不共享进程空间。
- **文件操作互斥**：对同一工作目录的写操作通过文件锁串行化。会话存档文件的写入操作同样加锁串行化。
- **资源限制**：可配置单个会话的最大并发工具调用数和子进程数。

### 2.12 长期记忆管理器

系统在用户目录下维护一个记忆库，路径为 `~/.devo/memory/`，分为两部分：

- **用户记忆**：按用户 ID 存储（如 `user-<user>.md`），包含跨项目的个人偏好、习惯等。
- **项目记忆**：按工作目录路径的哈希分片存储（如 `projects/<hash>.md`），包含与该目录关联的项目级约定、环境信息、踩坑经验等。

**记忆存储模型**：
- 每条记忆采用 `type + key` 的键值对模型。`type` 取值为 `user` 或 `project`，`key` 为记忆的唯一标识。
- 同一 `type + key` 组合唯一，后续写入自动覆盖前值（Upsert）。
- 每条记忆包含字段：`id`、`type`、`key`、`content`、`source`（`manual` 或 `auto`）、`created_at`、`updated_at`。

**关键机制**：
- **项目识别**：项目记忆的键是**规范化的工作目录绝对路径**。同一工作目录下的所有会话共享同一份项目记忆；不同目录即使对应同一代码仓库，也视为不同项目。
- **手动更新**：用户通过 API 直接添加/更新记忆，`source` 标记为 `manual`。
- **自动更新与降噪**：代理循环中，当用户明确要求记住某信息（"记住这个"）或系统通过启发式规则检测到用户对 AI 行为的纠正时，记忆管理器生成一份记忆更新草案（包含建议的 `key` 和 `content`）。为降低审批打断频率，系统采用以下降噪策略：
  - **批量合并**：在同一会话中，若连续多次触发记忆更新，系统将合并这些更新为一次审批请求，而非每次单独弹窗。
  - **静默学习模式**：当用户的审批策略将 `memory_update` 设为 `auto_approve` 或更高级别时，记忆更新完全静默执行，仅在 SSE 推送 `memory_updated` 通知事件。用户可事后在"记忆面板"中集中查看和管理。
- **检索**：每次构建上下文时，记忆管理器根据当前用户和会话工作目录，从对应记忆中检索最相关的若干条（基于向量相似度或关键词匹配），将其注入系统提示词。
- **并发安全**：对同一记忆文件的写入操作加锁串行化，后写覆盖前写。

### 2.13 经验固化器

当用户将一个会话标记为 `Completed`（通过 `POST /complete` 接口），或主动触发"固化"操作时，经验固化器启动：

1. 获取该会话的完整消息历史，过滤掉无关事件。
2. 调用一个轻量级 LLM 分析此会话，提炼：任务目标、步骤序列、关键决策、使用的工具、遇到的陷阱及解决方案。
3. 将分析结果格式化为一个符合 **Skills 规范** 的技能包，生成 `SKILL.md` 文件，包含提示词和必要的约束。
4. 根据当前审批策略判断是否需要用户确认。若需审批，则推送 `approval_required` 事件（`operation_type: solidify_skill`），展示新技能内容；若策略为自动批准，则直接存入技能库并推送 `skill_solidified` 通知事件。
5. 审批通过后，将其存入 `~/.devo/skills/`（可配置），并自动注册到 Skills 管理器。
6. 用户可随时手动编辑或删除由固化器生成的技能。

### 2.14 Skills 管理器

Skills 管理器负责统一管理三种来源的技能，并在构建上下文时向系统提示词注入指令。

**三种来源**：

| 来源 | 存储位置 | 优先级 | 说明 |
| :--- | :--- | :--- | :--- |
| **项目内 Skills** | `<工作目录>/.devo/skills/` | 最高 | 随 Git 版本管理，团队共享，项目专用。 |
| **全局/进化 Skills** | `~/.devo/skills/` | 中 | 用户个人积累（含经验固化器生成的技能），所有项目可用。 |
| **社区/商店 Skills** | `~/.devo/skills/` 或符号链接 | 可配置 | 从官方或第三方市场安装，可升级。 |

**加载策略**：
- 会话启动时，Skill 管理器自动扫描工作目录下的 `.devo/skills/` 和全局 `~/.devo/skills/`。
- 构建上下文时，按优先级顺序合并激活的 Skill 指令：项目内覆盖全局/进化，全局/进化覆盖社区。同名 Skill 以高优先级为准。
- 用户可通过接口在会话中动态启用/禁用特定的 Skills，也可在 `agents.md` 或配置文件中声明"仅使用以下 Skills"来限制加载范围。

### 2.15 agents.md 规则加载器

在代理循环构建上下文时，系统检查工作目录根目录下是否存在 `agents.md`（或 `.devo/rules.md`）文件。若存在，则读取全文并作为一段固定的系统消息注入，放置在 Skills 指令之后、长期记忆之前。这使得团队可以将项目级的编码规范、架构约束、安全红线等以文件形式固定下来，并纳入版本控制。

### 2.16 会话存档

为了让会话成为用户可直接查看、引用和管理的"数字资产"，系统在数据库持久化之外，自动为每个会话生成人类可读的 Markdown 存档文件。

**存储位置**：采用与 Skills 和 Memory 一致的分层策略。

| 类型 | 存储位置 | 说明 |
| :--- | :--- | :--- |
| **项目会话存档** | `<工作目录>/.devo/sessions/<session_id>.md` | 与项目绑定，可随 Git 版本管理。 |
| **全局会话存档** | `~/.devo/sessions/<session_id>.md` | 未绑定工作目录的会话（如独立对话）存储于此。 |

**存档文件格式**：Markdown 文件，包含会话的完整记录。

```markdown
# 会话：修复订单系统支付回调Bug

- **会话 ID**: sess_abc123
- **创建时间**: 2026-06-17 14:30 UTC
- **最后活跃**: 2026-06-17 16:00 UTC
- **状态**: Completed
- **工作目录**: /home/user/projects/order-system
- **Token 消耗**: 输入 12,000 / 输出 3,500 / 合计 15,500
- **压缩次数**: 1

---

## 用户
支付回调接口在支付宝异步通知到达时偶发 500，帮我排查。

## 助手
我先看看回调处理的代码。

## 系统
[工具调用: search_codebase] 搜索 "notify_url|callback|alipay" ...

## 助手
找到问题：`payment/callback.py` 第 47 行，签名校验失败时直接 `raise`，没有捕获异常返回 200。

## 系统
[工具调用: edit_file] payment/callback.py 第 45-50 行 ...

## 助手
已修复，将异常捕获后返回 200 响应，同时记录错误日志。

---

## 附录：上下文压缩摘要（第1次压缩）
早期对话（msg_001 - msg_020）摘要：用户描述支付回调 500 问题...
```

**生成与更新**：
- **实时追加**：代理循环中，每当产生新的消息（用户消息、助手回复、工具调用结果、系统消息），系统**异步追加**到存档文件末尾。不阻塞代理循环。
- **触发时机**：
  - `message_complete` 事件后追加助手回复。
  - `tool_result` 事件后追加工具调用结果。
  - 用户发送消息后追加用户消息。
  - 系统生成消息（回滚记录、崩溃恢复提示、上下文压缩摘要、工具调用上限暂停提示等）后追加系统消息。
- **文件锁**：写入时对存档文件加锁，避免并发写冲突。
- **上下文压缩处理**：当发生上下文压缩时，压缩的原始消息在存档中保留完整内容，同时在存档末尾追加"上下文压缩摘要"附录，标记哪些消息已被压缩及其摘要内容。这保证了存档始终是**人类可读的完整记录**，不丢失任何细节。

**存档与数据库的关系**：

| 层面 | 数据库 | 存档文件 |
| :--- | :--- | :--- |
| **用途** | 运行时状态、API 查询、SSE 事件 | 用户可读、可编辑、可版本管理 |
| **内容** | 完整消息历史（含内部元数据） | 人类可读的消息转录、Token 统计、压缩摘要 |
| **更新** | 实时（事务性） | 异步追加（最终一致） |
| **权威性** | **是**（系统唯一真相源） | 否（仅用户视图，可能与数据库不一致） |
| **同步方向** | 数据库 → 存档文件 | 单向导出，不反向写入 |

- **用户手动编辑**：用户可以直接编辑存档文件（如修改注释、删除敏感信息），但这**不影响数据库中的原始记录**。存档是用户的"笔记"，数据库是系统的"日志"。
- **崩溃后的恢复**：存档文件不需要特殊处理。系统以数据库为准重建会话，存档文件自然追加后续内容。若不一致，用户可手动调用 `POST /sync-archive` 重新生成。

**用户价值**：
- **直接查看**：在项目目录 `.devo/sessions/` 下找到所有会话，用任何文本编辑器打开。
- **引用成果**：在新对话中说"参考 `.devo/sessions/sess_abc123.md` 中的方案"，AI 可以直接读取。
- **分享协作**：把存档文件复制给同事，或提交到 Git，作为 AI 辅助开发的审计记录。
- **备份恢复**：存档文件本身就是一个完整的会话备份。如果数据库损坏，可从存档文件手动重建会话。

## 3. 任务处理层详细设计

任务处理层实现核心层需要的所有工具，并强制实施路径安全约束，采用**原生系统环境 + Python 统一执行器**作为沙箱方案。

### 3.1 工具集与路径安全

所有工具由任务处理层定义并暴露给 LLM。包含内置工具和通过 MCP 客户端动态发现的工具。

**内置工具**

| 工具名称 | 功能 | 需要审批 | 审批风险等级 | 安全约束 |
| :--- | :--- | :--- | :--- | :--- |
| `write_file` | 将完整内容写入指定文件（新建或全量覆盖） | 是 | 中 | 强制限定路径在工作目录内；覆盖已有文件时审批事件携带 diff |
| `edit_file` | 精确编辑文件，通过查找替换（`old_str`→`new_str`）或 unified diff patch 应用修改 | 是 | 中 | 强制限定路径在工作目录内；审批事件携带模拟生成的 diff |
| `read_file` | 读取工作目录下的文件内容 | 否 | - | 强制限定路径在工作目录内 |
| `list_files` | 列出目录结构 | 否 | - | 强制限定路径在工作目录内 |
| `execute_command` | 在工作目录中执行任意 shell 命令 | 是 | 高 | 执行前路径越界检查 + 命令黑名单过滤；统一通过 Python 中介执行 |
| `search_codebase` | 在项目中搜索文本或模式 | 否 | - | 强制限定在工作目录内搜索 |

**`edit_file` 工具详细设计**：
- **参数**：
  - `path`：目标文件路径（相对于工作目录）。
  - `mode`：`"replace"` 或 `"patch"`。
  - 若 `mode="replace"`，需提供 `old_str`（待替换的精确原文本）和 `new_str`（替换文本）。系统在文件中定位 `old_str`，若匹配不唯一则拒绝执行并返回错误。
  - 若 `mode="patch"`，需提供 `patch`（标准 unified diff 文本）。系统在工作目录下使用内部补丁引擎应用该 diff。
- **审批时的 diff 生成**：在推送审批请求前，系统读取文件当前内容，模拟应用编辑并生成新旧内容 diff，附加到 `approval_required` 事件的 `details.diff` 中。

**`write_file` 工具的审批增强**：
- 当目标文件已存在时，任务处理层在准备审批事件时，自动读取文件的当前内容，与待写入内容计算 diff（unified diff 格式），并将 diff 附加到事件的 `details.diff` 中。新建文件时无需 diff。

**MCP 动态工具** 通过 MCP 协议从外部服务器发现，其声明和安全约束由 MCP 服务器负责。

**路径安全强制规则**：
- 所有接受路径参数的文件工具，在操作前必须：
  - 基于工作目录将路径规范化为绝对路径。
  - 检查该绝对路径是否以工作目录为前缀。
  - 拒绝任何试图穿越到工作目录之外的操作，并返回明确的安全拒绝错误（不包含系统敏感路径信息）。
- 该检查在任务处理层统一实现，核心层无需关心路径安全。

### 3.2 MCP 客户端管理器

MCP 客户端管理器位于任务处理层，负责：

**两种来源**：

| 来源 | 存储位置 | 优先级 | 说明 |
| :--- | :--- | :--- | :--- |
| **项目内 MCP** | `<工作目录>/.devo/mcp_servers.json` | 最高 | 随 Git 版本管理，团队共享，项目专用。 |
| **全局 MCP** | `~/.devo/mcp_servers.json` | 中 | 所有项目可用。 |

- 根据配置文件连接到一个或多个 MCP 服务器。
- 在启动时及会话过程中，动态获取各 MCP 服务器提供的工具列表，并将其转换为内部统一的工具描述格式。
- 当 LLM 请求调用一个 MCP 工具时，将请求转发给对应的 MCP 服务器执行，并将结果返回给核心层。
- 处理 MCP 服务器的断线重连、工具变更通知等。

所有 MCP 工具都遵循相同的安全边界：其对文件系统的访问理论上不受 Devo 直接控制，故仅建议连接可信的本地或私有 MCP 服务器。

### 3.3 沙箱执行器：原生环境 + Python 统一执行

`execute_command` 工具的所有命令统一通过 Python 中介执行。Python 提供跨平台一致的执行环境、安全的命令转义层、以及可审计的执行记录。

**设计原则**：
- **统一性优先**：所有命令都走 Python 中介，不区分"简单"和"复杂"命令，确保跨平台行为一致。
- **安全性内置**：Python 的 `subprocess` 模块提供成熟的参数化执行能力，避免 shell 注入。命令字符串通过环境变量传递，而非拼接进 Python 源码，杜绝代码注入。
- **可审计性**：每条命令的执行方式对用户透明，审批界面展示完整的执行上下文。

**执行流程**：

1. **命令审批通过后**，任务处理层准备执行。
2. **构建 Python 调用**：
   - Go 代码将用户命令进行安全转义后，设置为环境变量 `DEVO_COMMAND`。
   - 调用 `python -c` 执行一段内置的固定 Python 脚本（编译进 Devo 或从资源文件加载），该脚本从环境变量读取命令并执行。
   - **不生成临时 `.py` 文件**，避免磁盘 I/O 和临时文件管理开销。
3. **Python 沙箱执行**：Python 脚本内部执行：
   - 通过 `os.chdir` 进入目标工作目录。
   - 进行**二次路径安全检查**，确保命令中引用的文件路径不越界。
   - 使用 `subprocess.run` 执行命令，捕获 `stdout`、`stderr`。
   - 应用**平台特定的资源限制**（详见平台能力矩阵）。
   - 设置执行超时（由 Agent 传入的超时参数控制）。
   - 将执行结果（exit code, stdout, stderr, 是否超时）以 JSON 格式打印到 stdout。
4. **结果返回**：Go 代码捕获 Python 子进程的 stdout（执行结果 JSON），解析后返回给核心层。
5. **子进程 PID 记录**：Python 解释器进程的 PID 记录到会话元数据中，用于崩溃恢复时的孤儿子进程清理。
6. **执行审计**：所有通过 Python 中介执行的命令内容，作为系统消息记录在会话历史中，并反映在会话存档中。用户可在审批界面和存档中查看完整的执行上下文。

**平台能力矩阵**：

系统诚实地面对跨平台差异，不在架构上伪装完全一致。以下矩阵声明了各平台当前版本的能力覆盖：

| 安全机制 | Linux / macOS | Windows |
| :--- | :--- | :--- |
| **路径安全（边界检查）** | 完全支持 | 完全支持 |
| **Python 中介执行** | 完全支持（Python 3.8+） | 完全支持（Python 3.8+） |
| **资源限制（内存/CPU）** | 通过 `resource.setrlimit` 实现 | **当前版本不支持**（需后续通过 Job Objects API 实现，详见扩展性章节） |
| **命令黑名单** | 基于 Unix Shell 语法（`rm -rf /`、`mkfs`、`dd if=` 等） | 基于 Windows Shell/PowerShell 语法（`format C:`、`del /f /s C:\*` 等），提供独立黑名单配置 |
| **高危管道过滤** | `curl ... \| bash`、`wget ... \| sh` 等 | `Invoke-WebRequest ... \| Invoke-Expression` 等 |
| **执行超时** | 完全支持 | 完全支持 |

- **Python 依赖声明**：Devo 依赖系统安装的 Python 3.8+。Python 是开发者的通用工具，绝大多数开发环境已预装。若未安装，Devo 启动时给出明确提示。
- **Windows 当前局限**：资源限制在 Windows 上标记为"当前版本不支持"。这不会阻塞命令执行，仅意味着在 Windows 上无法强制内存/CPU 上限。该能力计划在后续版本通过 Windows Job Objects API 补齐。

**命令安全过滤**：
- 命令在提交给 Python 执行器之前，先经过命令模式过滤器。
- 过滤器根据当前操作系统加载对应的黑名单配置：
  - **Unix 黑名单**：`rm -rf /`、`mkfs`、`dd if=`、`:(){:|:&};:`（fork 炸弹）等破坏性命令模式，及 `curl ... | bash`、`wget ... -O - | sh` 等高危管道组合。
  - **Windows 黑名单**：`format C:`、`del /f /s C:\*`、`Remove-Item -Recurse C:\`、`rd /s /q C:\` 等破坏性命令模式，及 `Invoke-WebRequest ... | Invoke-Expression` 等高危管道组合。
- 检测到匹配时，直接拒绝命令并返回安全错误，不进入 Python 执行环节。
- 过滤是尽力而为的辅助措施，在用户选择"完全信任"时是最后防线。

### 3.4 LLM 客户端封装

提供统一的 `LLMClient` 接口，支持流式对话和工具调用。核心职责：

- **多 Provider 适配**：封装不同大模型提供商的 API 差异，向核心层暴露统一接口。
- **Token 计数**：在每次 LLM 调用时，计算并返回 `input_tokens`、`output_tokens`，供 Token 计量器使用。原始计数数据来源于模型 API 响应（优先）或本地 tokenizer 估算（降级）。
- **流式输出**：支持逐 Token 流式返回文本和工具调用增量。
- **超时与重试**：可配置请求超时和自动重试策略。

## 4. 接口层详细设计

接口层完全封装核心层的功能，通过 **REST API** 接收指令，通过 **SSE** 推送实时事件。两者共享同一会话状态，无跨通道协调开销。

### 4.1 REST API

| 方法 | 路径 | 说明 |
| :--- | :--- | :--- |
| `GET` | `/api/v1/sessions` | 列出会话列表。支持 `?status=active\|completed\|archived\|all`、`?project=<path>`、`?limit=20&offset=0`。响应：会话摘要数组，每条含 `id`、`title`、`project_path`、`state`、`created_at`、`last_active_at`。 |

| `PUT` | `/api/v1/sessions/{id}/config` | 动态调整会话配置，包括工具调用上限 `tool_call_limit`。运行时调整即时生效。 |
| `GET` | `/api/v1/sessions/{id}/usage` | 获取会话 Token 消耗汇总，包含 `total_input_tokens`、`total_output_tokens`、`total_tokens`、`compression_count` 及可选的步骤明细。 |

所有修改会话状态的操作（取消、暂停、恢复、审批、回滚等）均为 REST 请求。服务端在收到请求后，直接操作对应会话的内部状态，并通过 SSE 将状态变更事件推送给客户端。

### 4.2 SSE 事件流

端点：`GET /api/v1/sessions/{id}/events`

客户端通过此端点建立单向的长连接，接收来自服务端的事件流。SSE 基于 HTTP，天然支持自动重连，并在重连时通过 `Last-Event-ID` 头告知服务端上次收到的事件 ID，服务端可从事件历史中补推遗漏的事件。

#### 核心事件类型定义

所有事件均为 JSON 结构，包含 `event` 字段和 `data` 负载。

| 事件类型 | 触发时机 | 关键负载字段 |
| :--- | :--- | :--- |
| `thinking` | 代理开始分析用户请求，或循环中进入思考步骤 | `message`: 描述当前思考重点 |
| `tool_call_request` | LLM 发出工具调用但还未执行（可能需审批） | `tool_name`, `params`, `requires_approval`, `risk_level` |
| `tool_result` | 工具执行完成 | `tool_name`, `success`, `summary`（结果摘要） |
| `approval_required` | 某个操作需要用户审批 | `approval_id`, `operation_type`（含 `file_write_new`、`file_write_overwrite`、`file_edit`、`execute_command`、`memory_update`、`solidify_skill`）, `risk_level`, `details`（含 `diff` 字段用于文件编辑操作，含 `command_context` 用于命令执行操作）, `timeout` |
| `approval_auto` | 某操作按策略自动批准，通知用户 | `operation_type`, `summary` |
| `approval_resolved` | 审批被响应或超时 | `approval_id`, `decision`, `source`（`user`/`timeout`） |
| `repair_attempt` | 代理检测到错误并尝试修复 | `attempt_number`, `error_summary` |
| `progress` | 当前步骤进度描述 | `step_description` |
| `token_usage` | 每次 LLM 调用完成后 | `step`, `input_tokens`, `output_tokens`, `session_total_tokens` |
| `context_compressed` | 上下文发生压缩 | `compressed_count`（压缩掉的消息数）, `tokens_removed` |
| `file_state_warning` | 回滚后检测到文件与对话可能不一致 | `message`: 警告详情 |
| `archive_updated` | 会话存档文件已更新 | `archive_path`, `last_message_id`（最后写入的消息 ID） |
| `error` | 发生异常或不可恢复错误 | `code`, `message` |
| `session_state_change` | 会话状态变更（Idle/Processing/Paused/Completed/Archived） | `old_state`, `new_state`, `reason`（`completed` / `cancelled` / `tool_limit_reached` / `error`） |
| `message_complete` | LLM 文本回复完成 | `message_id`, `full_text`, `total_step_tokens` |
| `memory_updated` | 长期记忆发生变更 | `memory_type`, `key`, `summary` |
| `memory_update_request` | 系统建议更新记忆，请求用户审批 | `memory_type`, `key`, `suggested_content` |
| `skill_solidified` | 经验固化完成，新技能已注册 | `skill_name`, `location` |
| `mcp_tool_discovered` | 发现新的 MCP 工具 | `tool_name`, `server_id` |
| `budget_warning` | 团队服务检测到 Token/金额预算达阈值 | `threshold_percent`, `current_usage`, `limit` |

`session_state_change` 事件增加 `reason` 字段，用于区分循环结束的原因：
- `completed`：任务正常完成。
- `cancelled`：用户主动取消。
- `tool_limit_reached`：达到工具调用上限暂停。
- `error`：不可恢复错误。

`approval_required` 事件的 `details` 字段增强：
- 对于命令执行操作（`operation_type: execute_command`），`details` 包含 `command_context` 字段，展示 Python 中介执行该命令的方式和执行上下文，增强用户对命令执行的信任。
- 对于文件编辑操作，`details` 包含 `diff` 字段，展示统一 diff 格式的新旧内容对比。

前端根据事件类型更新界面，实现实时反馈。所有控制指令（取消、审批、暂停等）通过 REST API 发送，与 SSE 事件流在服务端通过同一会话状态协调，无需额外同步机制。

### 4.3 暂停/恢复语义

- **暂停**：由用户主动调用 `pause` 接口，或在 `Processing` 状态下所有 SSE 连接均断开时自动触发。系统完成当前正在执行的原子步骤后进入 `Paused` 状态，通过 SSE（若仍有连接）或下次重连时的事件历史告知前端。
- **恢复**：用户重新连接 SSE 后调用 `resume`，或直接发送新消息（`POST messages`），系统从暂停点继续循环。恢复后系统会重新向 LLM 确认上一步骤的状态，确保不会重复执行已完成的工具调用。

### 4.4 取消操作的处理流程

1. 用户通过 UI 触发取消，前端发送 `POST /api/v1/sessions/{id}/cancel`。
2. 服务端立即为对应会话设置取消标记。
3. 代理循环在当前步骤结束时（或通过子进程中断机制尽快）检测到取消标记。
4. 清理正在执行的 Python 子进程，丢弃未完成的工具调用。
5. 将会话状态切回 `Idle`，通过 SSE 推送 `session_state_change` 事件（`reason: cancelled`）。
6. 用户界面收到状态变更后更新显示，对话可继续。
7. 异步更新会话存档，反映取消后的状态。

取消操作与 SSE 事件流之间没有时序竞态，因为所有状态变更均以服务端会话对象为唯一真相源，HTTP 请求修改标记，循环内部同步检查同一标记。

## 5. 文件版本管理与 Git 的关系

- **系统不管理版本**：没有自动快照，没有自动回退。
- **推荐的工作流**：用户为会话创建工作目录，初始化 Git 仓库。在 AI 编码过程中，用户可以随时手动 `git add` 和 `git commit`。
- **工具扩展**：可提供 `git_commit` 工具，让 AI 在用户批准的情况下代为提交，但非强制。
- **会话恢复时**：只恢复对话历史，用户需确保工作目录存在。若文件状态与对话历史不匹配，系统在回滚操作时会发出警告。
- **回滚后的文件不一致警告**：消息回滚完成后，系统自动检测工作目录中是否有回滚点之后产生的文件变更，若有，通过 SSE 推送 `file_state_warning` 事件。
- **会话存档与 Git**：项目内的会话存档文件（`.devo/sessions/*.md`）可以随代码一起提交到 Git，作为 AI 辅助开发的审计记录和团队知识沉淀。

## 6. 安全设计

- **路径安全是强约束**：所有文件工具和执行器必须实施工作目录边界检查，杜绝目录穿越攻击。
- **审批是核心防线**：采用操作风险分级机制，高风险操作始终需要用户确认，低风险操作自动批准但保持透明通知。所有审批请求设有超时，文件编辑操作的审批事件自动附带 diff，命令执行操作的审批事件附带执行上下文。
- **命令过滤**：在执行器之前，基于平台感知的双份黑名单模式拒绝明显的恶意命令和高危管道组合。Unix 和 Windows 各自维护独立的黑名单配置。
- **Python 中介安全**：命令通过环境变量传递，不拼接进 Python 源码，杜绝代码注入。Python 的 `subprocess` 模块提供成熟的参数化执行，避免 shell 注入。所有命令执行记录在会话历史中，可供审计。
- **记忆与技能隐私**：所有长期记忆和自动生成的技能默认存储在用户本地的 `~/.devo/` 目录下，不发生远程传输。用户可手动清理或迁移。
- **会话存档隐私**：会话存档文件存储在本地项目目录或 `~/.devo/` 下，与数据库保持单向同步。用户可手动编辑存档以移除敏感信息，编辑不影响系统内部记录。
- **MCP 安全**：仅建议连接本地或私有 MCP 服务器，避免工具泛滥带来的风险。
- **团队服务安全**：团队服务端仅接收 Token 消耗摘要和会话元数据，不上传任何代码内容、命令输出或完整对话。项目路径在上报前做哈希脱敏处理。远程协作功能需用户明确授权开启。
- **崩溃安全**：服务异常崩溃后，系统启动时自动扫描并重置非终态会话，清理孤儿子进程（Python 解释器进程），并插入系统消息告知用户。会话不会永久卡死在中间状态。
- **工具调用上限安全**：工具调用上限防止死循环或失控任务无限消耗 Token。达到上限后系统主动暂停并告知用户，用户可选择继续或放弃，预算完全可控。
- **原生环境风险**：Agent 以当前用户权限运行，依赖用户审批和信任。后续版本可引入操作系统级用户隔离。
- **工作目录限制**：Python 执行器确保命令在工作目录内运行，并检查文件路径越界。
- **提示注入防护**：工具返回的错误信息中不包含绝对路径等系统敏感信息。

## 7. 扩展性

- **工具集可扩展**：只需在任务处理层注册新工具，在系统提示词中添加定义，并实现路径安全逻辑。MCP 客户端管理器支持动态接入外部工具。`edit_file` 和 `write_file` 的双工具模式可根据场景扩展更多编辑原语（如 `delete_lines`、`insert_after` 等）。
- **Skills 可扩展**：支持项目内、全局、社区三种来源，经验固化器可持续生成私有技能。Skills 市场可扩展为组织级或公共注册表。
- **记忆与进化可扩展**：长期记忆管理器可更换后端（向量数据库等），经验固化器可升级分析模型以支持更复杂的技能提炼。
- **审批策略可扩展**：当前风险分级为三级（高/中/低），可扩展为更细粒度的多级分类；审批策略配置可从会话级扩展为用户级、团队级默认模板；可增加基于文件模式、操作时间的上下文感知审批规则。
- **执行器可替换**：当前基于 Python 中介的统一执行器可替换为容器（Docker/Podman）或轻量级虚拟机方案，实现更强的隔离。`Executor` 接口抽象化后，可支持多种执行后端。
- **平台扩展**：当前 Windows 上资源限制标记为"不支持"。后续版本可通过 Windows Job Objects API 补齐此能力，使 `execute_command` 在 Windows 上也具备完整的内存和 CPU 限制。
- **上下文压缩策略可替换**：压缩逻辑基于接口设计，可更换为更复杂的摘要模型。
- **持久化存储**：可用其他数据库替换，实现 `SessionStore` 接口。
- **传输层可替换**：当前采用 SSE + REST，若未来出现需要高频双向推送的场景，可升级为 WebSocket，不影响核心层与任务处理层。
- **团队服务可扩展**：统计引擎支持多租户模式，可接入 Prometheus + Grafana 实现可视化监控和告警。上报协议可扩展为 OpenTelemetry 标准。
- **Token 计量可扩展**：当前计量数据可直接用于成本估算和预算预警，未来可扩展为完整的计费系统和多模型成本优化推荐。
- **预算管控可扩展**：支持按团队、成员、项目设置 Token 或金额预算上限，达到阈值时触发 `budget_warning` 事件或阻止新会话创建。预算策略可通过团队服务统一配置下发。工具调用上限可扩展为分层预算（如总 Token 预算和步数预算双重约束）。
- **会话存档可扩展**：当前存档为 Markdown 格式，可扩展为 JSON、HTML 等格式。存档可扩展为"导出模板"，支持自定义内容（如仅导出代码变更、仅导出决策摘要等）。
